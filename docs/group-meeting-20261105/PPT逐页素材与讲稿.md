## 第一篇章　先完成 Dynaverse 核心协议复现

### 第 1 页　先把协议跑通，建立可以优化的基线

页面保留四行：

- 实现 Dynaverse/Dynamo、KZG、consistency、SRS 与公开验证的核心研究原型。
- 跑通初始证明 → 连续更新 → 分步重建 → 更新后公开验证。
- 保留 CPU reference，与优化路径逐算子、逐证明对照。
- 在此基础上进行算法实现、缓存、并行与资源管理优化。

页脚小字：当前是 ToyCircuit 上未加掩码的正确性研究原型，不等于完整零知识保证或原论文全部理论性能的复现。

口头讲法，约 45 秒：

> 第一个成果是完成了核心流程的工程复现。我们不只是让一个证明生成函数返回结果，还让 witness 更新之后，证明能够继续更新、需要时重建，并且通过公开验证。这个过程建立了后面优化所需的基线：我们可以比较改动前后是否计算一致、是否真的节省了时间。这里的成果范围是核心正确性原型，当前没有完整的零知识掩码。

来源：公开仓库 README“当前实现”；公开快照 a1e6b1e 的协议入口与增量更新测试。不要写“完整复现论文全部性能”。

### 第 2 页　协议流程：哪些阶段做了什么

插入图：[01_protocol.png](figures/01_protocol.png)；可编辑矢量版：[01_protocol.svg](figures/01_protocol.svg)。

页面文字：

| 阶段 | 一句话作用 |
| --- | --- |
| Setup | 建立电路相关公共参数 |
| 初始证明/Session | 构造并验证基准证明，建立连续更新状态 |
| Update | 检查变更并产生更新后的证明 |
| Rebuild | 需要时更新 anchor 和缓存，可被多笔 Update 分步推进 |
| Verify | 检查证明与当前公开输入的一致性 |

口头讲法，约 60 秒：

> 可以把 anchor 理解成一份基准账本，把 delta 理解成相对这份账本的补充记录。Setup 准备公共计算材料，Session 建立这份可更新状态。每笔 Update 处理变更，补充记录积累到条件后，再推进一份新账本的构建。新账本构建期间又发生的变更放在 overlay 中，切换时也不能丢掉。

脚注：Session 初始化会构造初始 anchor；独立 Prove 测量与 Session 初始化是不同 API。Rebuild 是 Update 内实际执行的工作时，不能与父 Update 用时重复相加。

### 第 3 页　更新协议有怎样的源码证据

页面左侧放教学流程：

~~~text
规范化变更 → 检查受影响约束 → 生成增量证明
                       ↓
             必要时按预算推进重建
                       ↓
          校验通过后提交新状态与证明
~~~

页面右侧放实际测试的短摘录：

~~~rust
let proof = session.update(&Update {
    indices: vec![4*n+i, 5*n+i],
    values: vec![next, output],
}).unwrap();
assert!(vk.verify(session.current_instance(), &proof).unwrap());
assert!(vk.verify_reference(session.current_instance(), &proof).unwrap());
~~~

口头讲法，约 60 秒：

> 测试里会同步更新一条乘法输入线和它的输出线，随后分别调用正式验证和 Reference 验证。真实实现先检查受影响门的约束，再在事务内准备新证明和必要的重建。只有所有检查成功后才提交；失败时回滚。这使优化路径可以与独立参考实现进行正确性对照。

重要补充：调用方负责提供一致的新 witness 变更；Update 不会自动根据输入计算整个电路的新 witness。

源码脚注：公开快照 a1e6b1e；crates/protocol/tests/incremental_rebuild.rs:23；crates/protocol/src/dynaverse/rebuilding.rs:178、211、224、335、361、420、250。这是历史代码证据，本次准备材料未重跑测试。

备份讲法：证明对象的组成是 anchor + 可选 delta + 版本号；这是结构组成，不是所有证明项都线性相加。

## 第二篇章　优化原理

### 第 4 页　优化围绕三个问题展开

页面保留三组对应关系：

| 问题 | 优化原则 | 对应实现 |
| --- | --- | --- |
| 相同准备反复做 | 准备一次，多次复用 | 固定基点表、NTT 计划、固定 G2 数据缓存 |
| 小变化牵动全量处理 | 优先计算变化贡献 | 稀疏线性承诺、冻结快照、分步重建 |
| 独立任务排队执行 | 并行和批量组织 | CPU 局部池、cache 方程并行、GPU 批提交 |

口头讲法，约 30 秒：

> 我们先区分哪些工作与新数据有关、必须重算，哪些材料没有变、可以复用。再把能独立执行的工作并行化。这三个问题贯穿后面的优化。

脚注：这些原理大多是已有算法和工程方法，本项目的工作在于适配协议路径、正确性约束和资源限制，不能把它们都称为原创密码学算法。

### 第 5 页　CPU：固定基点查表，减少重复算术准备

插图：[02_fixed_base.png](figures/02_fixed_base.png)。

页面原理：

- 大量 sᵢG 使用相同基点 G。
- 4-bit 窗口表提前保存各窗口所需曲线点。
- 标量分段 → 查表 → 累加，避免反复准备相同倍点。
- 同时复用 NTT 计划，并让独立 MSM 任务使用有界线程池。

口头讲法，约 60 秒：

> 这相当于先建立一套可重复使用的计算材料。固定基点表服务于反复出现的同一个 G；NTT 计划服务于同长度、同域的变换；线程池让独立任务同时执行。三项组合的主要收益集中在 Setup。NTT 本身仍要做蝶形运算，不能说缓存一个计划就消除了整个变换。

可加一个小结果框：本地 n=1024，CPU Setup 12.872→0.505 s，25.51×；小规模历史参考与组合候选，三对独立进程中位数。

脚注：固定表首次构造计入候选 Setup；25.51×不能只归给窗口表，也不能当作 H200 CPU/GPU 倍率。

### 第 6 页　GPU：不仅并行，还减少昂贵求逆与校验【可选/备份】

插图：[06_gpu_setup.png](figures/06_gpu_setup.png)。

页面展示三行机制：

| 机制 | 原来 | 改后 |
| --- | --- | --- |
| 固定基点生成 | 重复做标量乘准备 | 窗口表与设备批量生成 |
| 批量归一化 | 逐点求逆 | 每 128 点 tile 一次求逆，加乘法与回代 |
| G2 子群检查 | 完整阶乘法谓词 | BN254 专用 Frobenius63 等价关系 |

口头讲法，约 45 秒：

> GPU 适合批量任务，但如果每个点的处理本身很昂贵，仍然会慢。归一化利用批量求逆减少昂贵运算；子群检查利用固定曲线的结构选用更便宜的等价判定。这里没有取消规范编码、曲线和子群检查。

脚注：GPU63 是早期本地显式路径，拥有其自身的实验范围；后期 H200 主结果不能全部归给该校验优化。固定曲线之外不能直接照搬此关系。

### 第 7 页　增量：只计算变化贡献，必要时刷新基准

插图：[03_incremental.png](figures/03_incremental.png)。

页面中心公式：

$$C(W₀+ΔW)=C(W₀)+C(ΔW)$$

下方三条：

- 不变承诺继续复用，只补变化项贡献。
- 变化积累后冻结快照，按 Update 预算推进 Rebuild。
- 新变化记 overlay，新 anchor 通过检查后再切换。

口头讲法，约 60 秒：

> 这类似给已有账本增加补充记录。线性承诺允许我们直接计算少量变化对承诺的贡献。但是乘法约束有交叉项，不能只把证明简单相加；差量记录也不能无限积累，因此要重建新的 anchor。优化的是重复处理和工作分摊，不是让所有阶段都只花与变化个数成正比的时间。

脚注：分步 Rebuild 是 Update 推进的预算状态机，不等同于另开后台线程；完整重建与验证仍可能访问全域。

备份公式：Δ(fg)=fδg+gδf+δfδg，交叉项不能漏掉。

### 第 8 页　缓存：固定材料只算一次，变化后的方程仍重验

插图：[04_cache.png](figures/04_cache.png)。

页面原理：

$$D_i=τG₂-ω_iG₂$$

- 相同 SRS 和域根，得到相同 Dᵢ。
- affine divisor 缓存避免重复构造点。
- prepared-G2 缓存避免重复做配对准备。
- 每次新证明仍独立执行相应配对方程检查。

口头讲法，约 60 秒：

> 我们缓存的是固定量具，不是上一件产品的合格结果。Dᵢ 与本次 witness 无关，所以可以提前构造；变化后的 opening 和承诺仍要进入新的独立方程。这样不会因为过去验证成功就跳过当前检查。

结果框：H200 n=65536，全域 divisor Off→On，两笔 Update 合计 379.445→292.006 s，降时 23.04%。

脚注：独立历史消融，初始化新增构造成本已计入初始化；不是 CPU/GPU 比较。prepared 扩容是另一项对照，收益与内存成本不同。

### 第 9 页　执行组织：CPU 独立检查并行，GPU 小任务合并

插图：[05_parallel_batch.png](figures/05_parallel_batch.png)。

页面原理：

- 独立 cache 方程分给多个 CPU workers。
- GPU 相同形状的小任务组成批次，减少提交次数。
- 复用缓冲区，减少临时分配和读回交互。
- 并行受同步、内存带宽和任务大小限制。

口头讲法，约 50 秒：

> 这一层没有改变证明的数学关系，而是改变工作怎样交给硬件。独立方程可以由多个 CPU worker 同时检查。GPU 则尽量避免很多小任务反复提交。正式协议的配对检查仍然在 CPU，这也是 GPU 加速其他部分后主要的剩余瓶颈。

结果框：同历史二进制，H200 n=65536 的 cache workers 从 1 调到 8，完整重建 Update 146.247→35.387 s，4.133×。

脚注：固定 8 Slurm CPU slots，每个配置一个进程、两笔正式样本均值；不是 8 个独立物理核，也不是 GPU pairing。

## 第三篇章　结果、工程收尾与边界

### 第 10 页　主结论：本次 H200 Setup 加速超过 3 倍

主图：[result_h200_setup.png](figures/result_h200_setup.png)。

页面大字：

**Setup：60.23 s → 15.11 s**

**实测 3.985×；组会保守表述为“超过 3 倍”**

页面下方小表，不能省略负结果：

| H200 n=65536 | 优化 CPU / s | GPU / s | 现象 |
| --- | --- | --- | --- |
| Prove + aux | 663.003 | 665.867 | 没有明显改善 |
| 普通 Update | 0.150 | 0.223 | 小更新 GPU 更慢 |
| 完整重建 Update | 413.040 | 35.431 | 特定重建样本约 11.66× |

口头讲法，约 75 秒：

> 最适合拿来主汇报的是这张 Setup 图。在相同源码和 ToyCircuit 规模下，H200 相对优化 CPU 把约 60 秒缩短到 15 秒，实测约 4 倍，保守说超过 3 倍。收益有明显阶段差异：Prove 仍有 host 端重活，没有明显改善；普通 Update 很小，GPU 反而更慢；需要全量重建的 Update 才出现很大的 GPU 收益。所以我们按阶段报告，不给一个笼统的系统加速比。

可直接放入 PPT 的完整脚注：

> ToyCircuit n=2¹⁶，131072 个算术门；AMD EPYC 9V74 主机与 NVIDIA H200 NVL；源码 ffc7775；自研 Rust full_divisor_probe，std::time::Instant API 墙钟；CPU/GPU 各一个诊断进程。Setup/Prove 各一次观察；普通 Update 四笔中位数；重建 Update 两次预热后两笔均值。2026-10-29；不代表统一全流程加速比。

备份结果图：

- [CPU Setup](figures/result_cpu_setup.png)：历史小规模 CPU 参考与候选，不与本页倍率相乘。
- [cache workers](figures/result_cache_workers.png)：CPU cache 检查并行对外层 Update 的影响。

### 第 11 页　工程成果：减少重复持有，收敛主线【可选/备份】

页面文字：

- 共享不可变 SRS、复用工作区、缩短临时数组存活期。
- CPU anchor 请求分配峰值降低 14.48%。
- 保护原版和历史后，代码物理行减少 19.16%。
- 旧入口保留归档与恢复清单。

口头讲法，约 30 秒：

> 除了速度，我们也处理了内存重复持有和多条旧实验路径并存的问题。原版和历史有保护，主线只保留需要继续维护的入口。这改善了复现与维护成本，但减少代码行不代表提速。

脚注：内存数字为 Rust 请求分配计数，不是 RSS/显存峰值；行数含测试、注释和空行；精简候选没有新的完整 GPU/native 运行资格；完整大规模工程化仍未闭合。
